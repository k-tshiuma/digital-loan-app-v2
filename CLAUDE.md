# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

QuickLoan: a digital micro-loan application for foreign workers in Israel, split into a borrower app and an admin dashboard that share one SQLite database (`docs/app-separation-plan.md`). One npm workspace per folder below; run `npm install` once at the repo root (one `package-lock.json` there).

- `borrower-app/frontend/` — the borrower app: React 19 + Vite + Tailwind v4 (TypeScript, ESM), port 3000
- `borrower-app/backend/` — the borrower API: Express 5 (CommonJS), port 5000. Owns the database schema
- `admin-app/frontend/` — the admin dashboard (Back Office), same stack, port 3001
- `admin-app/backend/` — the admin API, port 5100. Staff tokens only
- `shared/frontend/` — package `@quickloan/ui-core`: frontend code both apps use (see Frontend architecture)
- `shared/backend/` — package `@quickloan/backend-core`: backend code both APIs use (see Backend architecture)
- `data/` — `database.sqlite` (tracked in git) and `uploads/` (gitignored). Both APIs use the same files
- `tests/integration/` — backend HTTP tests; `tests/contracts/` — frontend-vs-backend contract tests
- `scripts/` — `generate-hebrew-review.ts`, `generate_documents.js` (run from the repo root)
- The two apps never import from each other; anything both need goes in `shared/`.
- Backend settings come from the app's own `.env` (if any), then the repo-root `.env` (see `.env.example`); frontend settings from each app's `.env.example`.

The root `README.md` is the stock AI Studio template and is outdated. `implementation_plan.md` is the design for the current work, the 3-step approval workflow (statuses, notification matrix, decisions), and is the best record of intent. `implementation-plan01.md` is the older, finished phased plan (security, file uploads, analytics, SSE, etc.). `design/DESIGN.md` holds the design tokens (colors, typography) that the UI follows.

## Commands

Backend (from the repo root):
- `npm run start:borrower` and `npm run start:admin` start the two APIs (ports 5000 and 5100) on the same database; `npm run dev:borrower-api` / `dev:admin-api` for nodemon. Inside an app folder, `npm start` / `npm run dev` do the same. The admin API defaults to `ADMIN_PORT` 5100 and `DB_INIT=false`; the borrower API uses `BORROWER_PORT`, then `PORT`, then 5000.
- Tests are standalone scripts in `tests/integration/`, not a framework. Each starts the two real APIs as separate processes on the same database, runs assertions over HTTP, and exits non-zero on failure. The older ones (verification, guarantors, prefill, i18n) use `tests/integration/lib/splitApis.js`: `listen(port)` starts both APIs on port+1000/+2000 and a small router on `port` that sends staff tokens and `/api/auth/staff-*` to the admin API and everything else to the borrower API (header `X-Test-Target` forces one; `logMark`/`logsSince` read an API's log; `SPLIT_APIS_DEBUG=1` prints the request counts). Run one with:
  - `node tests/integration/test_verification.js`
  - `node tests/integration/test_guarantors_and_scoring.js`
  - `node tests/integration/test_returning_user_prefill.js`
  - `node tests/integration/test_i18n.js` (port 5005; also starts a borrower API on 5006 with `DEMO_MODE=false`)
  - `node tests/integration/test_workflow.js` (ports 5022/5023): the 3-step workflow, including the loan calculation checked against `shared/backend/fixtures/loan-calc-fixtures.json`; applicant requests on the borrower API, staff requests on the admin API. Run `npm run seed:staff` first: the test logs in as the seeded staff accounts and fails with a 401 at staff login if they don't exist.
  - `node tests/integration/test_route_matrix.js` (ports 5015–5018, needs the staff seed): calls every route as each identity (no token, bad token, borrower, each staff role) on each API, in demo and `DEMO_MODE=false` mode, and compares status codes with `tests/integration/fixtures/route-matrix.json`. It also checks that each API answers 404 for the other one's routes and that the token guards hold, that a staff status change on the admin API reaches the borrower's SSE stream on the borrower API, and that PDFs are generated. It is the safety net for the borrower/admin split. When you add a route or change access on purpose, run it with `--update` and review the snapshot diff.
  - `node tests/integration/test_tokens_and_cors.js` (ports 5041–5044, needs the staff seed): both APIs with demo mode off and only their own secret: tokens work only on their own API (secret, audience and type), old and forged tokens are refused, the production start-up checks, and CORS.
  - `node tests/integration/test_data_safety.js` (ports 5051/5052, needs the staff seed): two processes on one database: request numbers allocated at the same moment are all different, a client can't change an application's number, a staff message and a draft save at the same moment both survive, consent sent several times at once is recorded once, and a PDF request with an application in the body never stores it.
  - `node tests/integration/test_admin_network.js` (ports 5061/5062, needs the staff seed): the admin API's office/VPN limit (`ADMIN_ALLOWED_IPS`, `core/ipAllowlist.js`): allowed and refused addresses behind a pretend proxy, loopback always passing, and a malformed list stopping start-up.
  - `node tests/integration/test_session_cookies.js` (ports 5071–5074, needs the staff seed): the HttpOnly session cookies on both APIs: attributes, signing in by cookie (including SSE), CSRF header, each API reading only its own cookie, logout, CORS credentials, and the Secure flag in production.
  - `node tests/integration/test_split_backends.js` (ports 5031/5032, needs the staff seed): both APIs as separate processes: a borrower upload opens for staff on the admin API, simultaneous borrower and staff writes cause no server errors or `SQLITE_BUSY`, and each API keeps working when the other stops.
  - `node tests/integration/test_classic_flow_disabled.js` (ports 5081–5083, needs the staff seed): the borrower API with the classic wizard off (`ENABLE_CLASSIC_FLOW` unset): starting, saving or submitting a classic draft gets 403 `CLASSIC_FLOW_DISABLED`; submitted classic applications stay readable (history, PDF) and can be re-submitted after a requested document; the 3-step flow is unaffected. The tests that drive the classic wizard turn it on for the APIs they start (`lib/splitApis.js` does it for the older ones).
- Tests use the real `data/database.sqlite`. There is no separate test DB.
- Seed scripts: `npm run seed:staff` (`admin-app/backend/scripts/seed_staff.js`) creates one staff account per role (`admin@`, `reviewer@`, `service@`, `funding@quickloan.co.il`). Passwords come from `ADMIN_/REVIEWER_/SERVICE_/FUNDING_INITIAL_PASSWORD`, with defaults such as `Admin123456!`; `test_workflow.js` expects the defaults. Existing accounts are left unchanged. `node borrower-app/backend/scripts/seed_pending_application.js` creates an applicant waiting for Step 1 approval through the real API (borrower API running in demo mode; `API_URL` overrides the base URL).

Frontend: the borrower app (`borrower-app/frontend/`, port 3000) and the admin dashboard (`admin-app/frontend/`, port 3001) have the same scripts below, run inside the app folder (or `npm run dev:borrower` / `dev:admin` at the root). Each talks to its own API through `VITE_API_URL` (borrower default `http://localhost:5000/api`, admin default `http://localhost:5100/api`). `VITE_ADMIN_URL` (borrower app, default `http://localhost:3001`) is where old `/backoffice` and `/admin` links are sent; `VITE_BORROWER_URL` (admin app, default `http://localhost:3000`) is the staff login page's link back to the public site.
- `npm run dev`: Vite dev server
- `npm run build`
- `npm run lint`: type-check only (`tsc --noEmit`). There is no ESLint.
- `npm test`: Vitest + React Testing Library (jsdom). `npm run test:watch` for watch mode, `npx vitest run <path>` for one file. Tests live in `__tests__/` folders next to the code; setup is `src/test/setup.ts` (the app's message groups, then `@quickloan/ui-core/test-utils/setup`).
- Shared code has its own suite: `npm test` in `shared/frontend/` (runs with only the shared message groups). Contract tests: `npm run test:contracts` at the repo root. `npm run test:frontend` at the root runs the three frontend suites. Run them and the contract tests before committing frontend changes.

## Deployment

Production is one Ubuntu 24.04 server: nginx serves both built frontends and forwards each site's `/api` to its own API, pm2 runs the two APIs (one process each, never cluster mode), and both use one SQLite file. Files in `deploy/` (`deploy.sh <tag>`, `backup.sh`, `smoke.js`, pm2 and nginx config, env templates); procedures in `docs/deployment-runbook.md`. The Docker alternative (same env files; containers `borrower-api`, `admin-api`, `web` and one data volume) is in `deploy/docker/` (`Dockerfile`, `compose.yml`, `nginx.conf.template`, `deploy.sh`, `backup.sh`), procedures in `docs/docker-deployment.md`. `deploy/docker/nginx.conf.template` mirrors `deploy/nginx/quickloan.conf`; change both. Production-only settings: `LISTEN_HOST=127.0.0.1`, `TRUST_PROXY=loopback` (visitor IPs for rate limits and audit), and the staff seed refuses default passwords when `NODE_ENV=production`. The admin site can be limited to the office or VPN in two places with the same list: `deploy/nginx/quickloan-admin-access.conf` and `ADMIN_ALLOWED_IPS` for the admin API.

## Backend architecture

- Layout: `shared/backend/` (package `@quickloan/backend-core`) holds everything both APIs use: `core/`, `database.js`, `creditEngine.js`, `services/`, `routes/flow.js`, `assets/fonts/`, `fixtures/`, `loadEnv.js`. App code requires it as `@quickloan/backend-core/<path>`; files inside it require each other relatively and never require an app. Paths like `services/x.js` and `core/x.js` below mean `shared/backend/...`.
- Two APIs, both built on `core/appBase.js` (middleware, the flow route factory, health, 404, error handler):
  - `borrower-app/backend/server.js`: its own `routes/` (auth, account, uploads, classic applications + SSE, application detail, notification inbox). `rejectStaffTokens` refuses any staff token (401), so its handlers have no staff code. Starts the SSE status poller (`ssePoller.js`, see Real-time). Owns the schema.
  - `admin-app/backend/server.js`: its own `routes/` (demo staff tokens, account, application detail, application list, staff notifications, analytics, credit-rule config). `staffOnlyAuth` replaces `optionalAuth` (any non-staff or invalid token is refused, no demo identity even in demo mode) and `authenticateStaff` replaces `authenticate`.
  - Each exports `app` and only calls `listen` when it runs as the main module, which is how the tests start them in child processes.
  - A route that exists on one API answers 404 on the other (after the token check, so a request without a valid token gets 401 first).
- Routes go in the app whose users call them, and a handler only contains the code for that app's users (no `isStaff(req)` branches). Where both apps serve the same path (`GET /api/users/me`, `GET /api/uploads/:filename`, `GET`/`PUT /api/applications/:id`, the PDF), each has its own handler in `routes/account.js` / `routes/applicationDetail.js`, and what they share (saving, risk scoring, notifications, the PDF lookup) is in `core/classicApplications.js`. Mount order matters where paths overlap (e.g. `/api/applications/active/:userId` must come before `/api/applications/:id/pdf`), so keep the order in each `server.js`.
- `core/` holds the helpers all routes use: `config.js` (`DEMO_MODE`, `JWT_SECRETS`, `STAFF_ROLES`, `UPLOAD_DIR`), `auth.js` (tokens, `authenticate`/`optionalAuth`, the per-API guards, `requireStaff`, `canAccessUser`, OTP store), `applications.js` (`parseApp`/`writeApp`, request numbers, credit rules and risk score), `notifications.js` (classic-flow notifications), `sse.js` (SSE clients, `broadcastAppEvent`), `appBase.js` and `logPrefix.js`.
- `database.js` opens `DB_PATH` (default `data/database.sqlite`), turns on WAL mode with a 5 s busy timeout so two processes can share the file, and creates the schema on startup unless `DB_INIT=false` (only one process may own the schema; with `DB_INIT=false` the terms are not seeded either). WAL keeps recent writes in `database.sqlite-wal` (gitignored) until a checkpoint, so stop the APIs before committing `data/database.sqlite`. Schema changes are made by appending `ALTER TABLE ... ADD COLUMN` statements to the list there; errors are ignored when a column already exists. There is no migrations tool. JSON-shaped fields (guarantors, riskFlags, eligibilityBreakdown, profileData, …) are stored as TEXT and parsed or serialized in `core/applications.js` (`parseApp`/`writeApp`).
- Request numbers (`REQ-<year>-<n>`) come only from `nextRequestNumber()`, which takes the next value from the `request_counters` row for the year in one atomic statement, so the two processes never get the same number; a unique index on `applications.requestNumber` backs it up. The server assigns the number; `PUT /api/applications/:id` ignores one sent by the client.
- Concurrent writes: `updateFlowApp` in `routes/flow.js` writes only the columns a handler changed since the application was loaded (snapshot under a symbol key set by `getFlowAppById`/`getFlowAppByUser`), so a change the other process made meanwhile is kept; with an expected `flowStatus` it writes nothing (409) if the status moved. A change to one key inside a JSON column that the other side may also edit is merged in SQL with `json_set` (registration consent, adding a phone number). Load through those helpers before saving, or every column is written.
- Auth: `optionalAuth` runs globally. Then `app.use('/api', authenticate)` protects every route registered after it, so public auth routes (`/api/users/login`, `request-otp`, `verify-otp`, …) must be declared *before* that line. Staff endpoints use `requireStaff(...roles)`. Roles: `customer_service`, `credit_reviewer`, `system_admin`, `funding_entity` (plus `borrower`).
- **DEMO_MODE** is on unless `NODE_ENV=production` or `DEMO_MODE=false`. It enables a fixed OTP `123456`, `/api/auth/staff-token` role-picker tokens, mock Google login, codes echoed back in responses, and a fallback `demo_user` identity when no or invalid token is sent. Keep this in mind when reasoning about access control.
- Tokens: borrower tokens are signed with `BORROWER_JWT_SECRET` and audience `quickloan-borrower`, staff tokens with `ADMIN_JWT_SECRET` and `quickloan-admin` (`core/auth.js` `signToken`/`verifyToken`, HS256 only). Both fall back to `JWT_SECRET`, then to a dev constant outside production. In production each API must have its own secret and they must differ, or it refuses to start (`assertJwtSecrets`). The borrower API refuses any token that claims to be staff, even one it can't verify. CORS: each API allows only its own Vite dev site locally, none in production (same origin behind nginx); `CORS_ORIGIN` overrides. The frontends sign out when a request made in a session gets a 401 (`SESSION_EXPIRED_EVENT` in `apiCore.ts`).
- Browser sessions are HttpOnly cookies (`core/sessionCookie.js`): every sign-in response also sets the API's own cookie (`ql_borrower` / `ql_staff`; `HttpOnly`, `SameSite=Strict`, `Path=/api`, `Secure` in production, `COOKIE_SECURE` overrides), and `POST /api/auth/logout` on each API deletes it. `readToken` takes the `Authorization` header first (tests, API clients), then this API's cookie, then `?token=` on GETs. CSRF: a request signed in by the cookie that changes something needs `X-QuickLoan-Request: 1`, or it gets 403 `CSRF_CHECK_FAILED` (`csrfGuard`, before the auth middleware). A bad cookie is deleted in the response. When you add a route that signs a token, wrap it in `setSessionCookie(res, kind, token)`. `tests/integration/test_session_cookies.js` covers all of this.
- Two scoring systems, which are different things:
  - `creditEngine.js`: the rule-based risk pre-screen (riskScore/riskLevel/riskFlags). Thresholds can be overridden through `PUT /api/config/credit-rules`, which persists them in the `app_config` table. It is advisory only and never blocks a submission.
  - `services/eligibilityScoring.js`: the indicative eligibility score. **It is mirrored in `shared/frontend/services/eligibilityScoring.ts`.** Keep both in sync when you change factors or weights.
- Uploads: multer writes to `UPLOAD_DIR` (default `data/uploads/`, gitignored), metadata goes in the `uploaded_files` table, and files are served via `GET /api/uploads/:filename`.
- Real-time: `GET /api/applications/:id/events` is SSE. Status changes in `PUT /api/applications/:id` broadcast to subscribers. Two screens listen with `EventSource`: the classic `Step11StatusTimeline`, and the 3-step flow (`utils/useFlowLiveUpdates.ts` in the borrower `App.tsx`: a `status` event reloads the application and moves the applicant to the open step or the hub, an `updated` event reloads it without leaving the screen). With split backends, staff changes happen in the admin process, whose broadcasts reach no streams; the borrower API's `borrower-app/backend/ssePoller.js` checks the applications that have an open stream every `SSE_POLL_MS` (default 5000) and sends the same `status`/`updated` events. `core/sse.js` remembers what was already sent so nothing is sent twice.
- `services/smsService.js` (Twilio) and `services/emailService.js` (SMTP) log mock output to the console when their env vars (`TWILIO_SID`/`TWILIO_TOKEN`, `SMTP_USER`/`SMTP_PASS`) are unset. Borrower-facing backend text (status SMS/notifications, OTP, password reset) lives in `services/messages.js` (en + he, falls back to English); add new texts there, not inline in route code. `pdfService.js` streams an application summary PDF with pdfkit, in English or Hebrew (`?lang=`). PDF labels are in `pdfLabels.js` (stored-value labels must match the frontend; a frontend test checks this). Hebrew text must go through `pdfRtl.js` (bidi reordering for pdfkit), and Heebo fonts are in `shared/backend/assets/fonts/`.
- **3-step approval workflow** (applications with `flowVersion = 2`). This is the default applicant flow:
  - `services/workflow.js` has no I/O. It defines the `flowStatus` values (`LEAD_REGISTERED` → `PENDING_STEP1_APPROVAL` → `STEP1_APPROVED` → … → `PENDING_FINAL_PROCESSING` → `LOAN_APPROVED`/`LOAN_REJECTED`, plus `STEPn_CHANGES_REQUESTED`), the allowed transitions, the Back Office filter groups (`groupOf`) and which staff roles may view, decide or message. Every state change in `routes/flow.js` is checked against these tables, so add new transitions there.
  - `routes/flow.js` exports `createFlowRoutes(deps)`. `core/appBase.js` passes the helpers in; each API calls its half: `registerApplicantPublic(app)` (`/api/flow/register`, `/api/flow/google`) and `registerStaffPublic(app)` (`/api/auth/staff-login`) before the `authenticate` line, then `registerApplicant(app)` (registration consent, `/api/flow/account/contact`, terms, step draft/submit, final documents) and `registerStaff(app)` (the staff list, detail, step decision, final decision, message, delivery retry and audit endpoints under `/api/flow/applications`) after it.
  - The classic wizard is off unless `ENABLE_CLASSIC_FLOW=true` on the borrower API (`CLASSIC_FLOW_ENABLED` in `core/config.js`, `refuseClassicDraft` in `core/classicApplications.js`): `GET /api/applications/active/:userId` and `PUT /api/applications/:id` for new or unsubmitted classic applications answer 403 `CLASSIC_FLOW_DISABLED`. Submitted classic applications stay readable, staff can still change their status, and the borrower can re-submit one after a requested document. The frontend link has its own `VITE_ENABLE_CLASSIC_FLOW`; for local classic testing turn both on.
  - The legacy `PUT /api/applications/:id` refuses `flowVersion = 2` applications. Change them only through `/api/flow` endpoints. `GET /api/applications` (staff) includes all flow applications, not only submitted ones, and masks the bank account. Staff reveal it through `GET /api/flow/applications/:id?revealBank=1`, which is audited.
  - Entry rules: an account is only created through registration, which requires `registration.locationGranted === true` and `disclaimerAccepted === true` (`LOCATION_REQUIRED` / `DISCLAIMER_REQUIRED`; a new Google account without it gets `REGISTRATION_REQUIRED`). Accounts that signed in elsewhere give the same consent through `registration-consent` before Step 1. `POST /api/flow/account/contact` adds a missing phone (SMS-verified) or email once and never changes an existing one (`CONTACT_LOCKED`). In Step 1, phone and email always come from the account; a name different from the account name is a legal-name correction that needs `personal.legalNameConfirmed`, updates the account name on submit and is audited (`LEGAL_NAME_CORRECTED`).
  - `services/flowValidation.js` is the server-side authority for each step's data (`clean*` for drafts, `validate*` returns `{field: errorCode}`; the frontend translates the codes).
  - `services/loanCalculator.js` is a port of `calculateLoanRepayment`/`getServiceFeeForAmount` in `shared/frontend/config/appConfig.ts`. **Keep both identical.** The shared fixture is `shared/backend/fixtures/loan-calc-fixtures.json`.
  - `services/terms.js`: versioned General T&C and Service Fee texts (`terms_versions`). Applicants see the latest version, and each acceptance stores the version and the SHA-256 of the text (`terms_acceptances`). To publish new wording, add a version; don't edit an existing one.
  - Notifications: `services/flowMessages.js` holds the en/he texts and the `FLOW_EVENTS` matrix (in-app/SMS/email per event; `'optional'` email can be switched off with the `notifyEmailOptional` app_config key). `services/flowNotifications.js` sends them and logs each channel in `notification_deliveries`. A failed send never undoes the workflow step.
  - New tables: `application_step_reviews`, `application_step_submissions`, `audit_log`, `terms_versions`, `terms_acceptances`, `staff_users` (real staff accounts with bcrypt passwords, used by `/api/auth/staff-login`), `notification_deliveries`.
  - `services/dbHelpers.js` has promise wrappers (`dbGet`/`dbAll`/`dbRun`), `newId`, `sha256` and `safeJson`. New backend modules use them.

## Frontend architecture

- Layout: code both apps use lives in `shared/frontend/` (package `@quickloan/ui-core`, TypeScript source, no build step): `types.ts`, `config/appConfig.ts`, `services/{eligibilityScoring,storageCore,apiCore}.ts`, the shared components `DateInput`, `EligibilityScoreBar`, `ErrorBoundary`, and the i18n core (`i18n/{translations,LanguageContext,LtrText,format,options,apiErrors}` and `i18n/messages/{common,status,types,index}.ts`). App code imports it as `@quickloan/ui-core/<path>` (e.g. `@quickloan/ui-core/i18n/translations`); files inside `shared/frontend` import each other relatively and must never import from an app. Everything else below is app code (`borrower-app/frontend/src/` for the borrower app, `admin-app/frontend/src/` for the admin dashboard). Paths like `i18n/format.ts` below mean the shared copy. Each app's `src/index.css` has an `@source` line for `shared/frontend` so Tailwind generates the classes used there.
- `App.tsx` has two applicant flows, switched by `flowMode`:
  - **3-step flow** (`'intermediary'`, the default): `FlowEntry` (sign-in first; registration = location access → conditions → account, manual or Google; then, if needed, the consent or missing contact details; `flowGate` in `App.tsx` decides) → `Step1LeadGeneration` (Step 1 data only; name, phone and email pre-filled from the account and protected, name correctable to the passport name) → `Step2ApplicationCompletion` → `Step3FinalSubmission`, with `FlowStatusHub` between steps (`currentFlowStep` is `1 | 2 | 3 | 'hub'`). The state comes from the backend (`flowApplication`, a `FlowApplicationView` in `types.ts`), and each step needs a Back Office approval before the next one opens. The API methods are the `flow*` / `*FlowStep*` ones in `services/api.ts`.
  - **Classic wizard** (`'classic'`, behind the "classic wizard" link, which only shows when `VITE_ENABLE_CLASSIC_FLOW=true`, read by `utils/featureFlags.ts`; it skips the Back Office approvals, so it is off by default and in production builds): a numbered `currentStep` (1 Language → 2 Auth → 3–9 form steps → 10 Submission success → 11 Status timeline). Each step is a `components/StepN*.tsx`. The `Step1`/`Step2`/`Step3` names overlap between the two flows. Under Vitest `flowMode` defaults to `'classic'`, so the existing App tests exercise the classic wizard.
- The admin dashboard is `admin-app/frontend`: its `App.tsx` shows `StaffLoginGate` until there is a staff session, then `BackOffice.tsx` (staff console, including `AnalyticsDashboard`). For flow applications it loads `GET /api/flow/applications/:id`, normalizes it with `services/flowDetail.ts` (`normalizeFlowDetail`), and shows it in `FlowApplicationInspector` (step decisions, final decision, messages, delivery retry, audit). Staff text is in `admin-app/frontend/src/i18n/messages/backoffice.ts`. The borrower app has no Back Office code: its `App.tsx` sends `/backoffice`, `/admin`, `#admin` and `?backoffice` URLs to `VITE_ADMIN_URL` (`utils/portalRedirect.ts`). The two apps must never import from each other; shared code goes in `shared/frontend`.
- Two data layers:
  - `services/api.ts`: the backend client (`apiService`). Each app has its own: the borrower one has the applicant endpoints, `admin-app/frontend/src/services/api.ts` the staff ones. The request core it builds on is `shared/frontend/services/apiCore.ts`: base URL (`VITE_API_URL` or `http://localhost:5000/api`), `request()`, `ApiError`, `isNetworkError`, `resolveFileUrl`, `downloadApplicationPdf`, `endServerSession` (logout), the borrower session record `authTokens`, and `setSessionStore()`. The apps never store or send the token: `request()` sends `credentials: 'include'` and the `X-QuickLoan-Request` header, file URLs and the SSE stream (`withCredentials`) rely on the cookie, and the session record (`quickloan_session_v2`; the admin app's `quickloan_staff_session_v2`) keeps only the user id or staff role, the expiry and a per-sign-in id. Each app has one session that every request, file URL and PDF download uses: the borrower app the default `authTokens`, the admin app its staff session (`admin-app/frontend/src/services/staffSession.ts`, installed by its `api.ts`), so the borrower bundle contains no staff code. `api.ts` re-exports these names, so app code imports them from `services/api`.
  - `services/storage.ts`: the `storageService` that keeps a localStorage/in-memory model of users, applications, notifications, audit events and config, with seeded demo applications. It handles draft persistence and offline backup. Each app has its own, built on `StorageCore` in `shared/frontend/services/storageCore.ts` (storage keys, seed data, load/save, and what both apps do: read and save an application, status changes, audit, notifications). The borrower one adds the local sign-in helpers and OTP, the session user (`adoptUser`/`restoreSession`), drafts and returning-user prefill, submission and the inbox; the admin one adds the audit list, the simulated funding handoff, the exports and the config. Put a new method in the app that calls it, and in the core only if both do. Components often call both layers, so check which one a change belongs in.
  - Session user: after any backend login, `App.handleAuthenticated` passes the user through `storageService.adoptUser()`, so the session keeps the backend id (the `sub` in the JWT) and the local copy made by the `storageService` login helpers is merged into it. On start-up the user comes from `storageService.restoreSession(authTokens.subject())`. Never put a locally generated user id into the session while a backend token exists, or API calls for the user return 403.
- Shared types: `types.ts`. Business limits (loan amounts, repayment periods, fees, min age, visa validity): `config/appConfig.ts`.
- i18n: `i18n/translations.ts` holds the dictionaries and a `t(lang, key)` helper. `i18n/LanguageContext.tsx` (`LanguageProvider` in `main.tsx`, `useI18n()` hook) owns the current language, saves it in localStorage (`quickloan_language`), and sets `<html lang dir>`. Hebrew is RTL.
  - Only English and Hebrew are enabled (`enabled` flag in `SUPPORTED_LANGUAGES`, `ENABLED_LANGUAGES`). Thai, Chinese and Filipino are on hold: hidden from pickers, dictionaries kept. New UI strings need `en` and `he` entries only. The `describeDictionary` guard enforces en/he key parity in every suite.
  - New UI strings go in `i18n/messages/*.ts` (grouped by area, en + he), not in the base dictionary. Groups both apps use (`common`, `status`, `eligibility`, `validation`, `labels`) are in `shared/frontend/i18n/messages/` and listed in its `index.ts`. Any key that shared code uses (the eligibility bar, `options.ts` labels, visa validation) must be in a shared group, because each app only has its own groups. App-only groups are registered at start-up by each app's `src/i18n/appMessages.ts` (`registerMessages`), which `main.tsx`, the test setup and `scripts/generate-hebrew-review.ts` import first: the borrower app has `auth`, `wizard`, `leadFlow`, `entry`; the admin app has `backoffice`. Keys must be unique across all groups. Never hard-code visible text: the guards in `shared/frontend/test-utils/i18nGuards.ts` (run by each suite's `i18nGuards.test.ts`) scan components for English JSX text and check every `t()` key exists in that app's dictionary. Use `{/* i18n-ignore */}` only for brand names or demo data.
  - Stored values (dropdown options, statuses, roles, risk flags, document codes) stay English. Show them with the helpers in `i18n/options.ts` (`optionLabel`, `statusLabel`, …). Show errors with `localizeError()` from `i18n/apiErrors.ts`.
  - Date fields use `<DateInput>` (`components/DateInput.tsx`, value is an ISO date), never `<input type="date">`, which shows the browser's format instead of the app's. The `describeNoNativeDate` guard enforces this.
  - Request numbers and phone numbers inside free text (notification messages) go through `<LtrText>` (`i18n/LtrText.tsx`) so they stay left-to-right in Hebrew.
  - The Hebrew review sheet for the native speaker is `docs/hebrew-review.csv`. Regenerate it after text changes with `npx tsx scripts/generate-hebrew-review.ts` (from the repo root). It reads both apps' dictionaries and the backend texts (`messages.js`, `flowMessages.js`, `terms.js`, `pdfLabels.js`), and keeps the reviewer columns. Legal keys are listed at the top of the script.
  - Numbers, amounts and dates: use `formatCurrency`/`formatNumber`/`formatDate`/`formatDateTime`/`formatTime` from `i18n/format.ts` (or the bound versions on `useI18n()`). Never use bare `toLocale*()` or hand-write `₪{…}`; The `describeBareLocale` guard enforces this. Translation strings take the already-formatted amount (`{amount}`) without their own `₪`.
  - Eligibility factor descriptions carry `descriptionKey`/`descriptionParams` in both scoring mirrors; keep the keys in sync too.
  - RTL: use logical Tailwind classes (`ms-/me-/ps-/pe-/start-/end-/text-start/text-end/border-s/e/rounded-s/e`), never `ml-/pr-/left-/text-right` etc. Directional icons need `rtl:rotate-180`. Phone numbers, codes, IDs and emails get `dir="ltr"` (inputs) or `<bdi dir="ltr">` (display). The `describePhysicalDirection` guard enforces the class and icon rules.
  - Language changes go through `handleLanguageSelect` in `App.tsx`, which also saves the choice to the user's account (`PUT /api/users/me/language`, accepts `en`/`he`).
  - Ongoing Hebrew work is tracked in `hebrew-localization-plan.md`.
